# Mini-Vera caller-pinned receipt gate and local replay ledger — SOURCE CANDIDATE

This additive module tests a more meaningful trust boundary than the same-user ephemeral self-signer in Draft PR #209. It accepts a signed fixed-source observation only when the **caller supplies the public key and its expected SHA-256 fingerprint separately from the receipt**, plus an expected source SHA-256, request SHA-256, turn SHA-256 and one 128-bit challenge. Nothing in the untrusted receipt can select the verification key or change the expected pin.

Module: `tools/mini_vera/pinned_host_evidence.py`, class `PinnedHostEvidence`. The verifier re-reads the fixed `tools/mini_vera/compose.py` bytes with the existing source/unsigned-manifest checks, compares the current file hash to the independently supplied expected digest, verifies the Ed25519 signature using PR #208's verifier, and verifies the signed source size against the actual file. Signature verification precedes any ledger write.

Successful verification attempts to atomically insert the challenge and receipt metadata into an external SQLite database (in an operator-selected existing directory outside the source/bundle). The challenge is a unique primary key, so a replay from another controller instance or a competing process is refused. A SQLite IMMEDIATE write transaction, FULL synchronous mode, quick integrity check and readback check guard ordinary database races and corruption. The SQLite database contains hashes, not signing credentials or private memory. The code never generates, exports or stores a private key, never loads a neural model, does not start a subprocess and never grants tool authority.

**Limits:** The database is ordinary same-user state, not a protected anti-rollback ledger. A same-user adversary who deletes or replaces it can replay an old signed receipt: the hostile test *demonstrates* this. Filesystem TOCTOU, attacker-controlled valid databases, trusted-clock tampering and caller-provided key-pin provenance are unqualified. Independently supplying a pin is a necessary precondition but this source module **cannot prove** that the caller pinned an authorized issuer. A same-user attacker who can change both the caller's pin and the database retains control. The flag `host_issuer_qualified=false` remains mandatory, and success is labeled only `PINNED_SIGNATURE_LOCAL_SOURCE_LEDGER_CONSISTENT`.

The present PR #209 ephemeral issuer is NOT a trusted issuer for this gate, because it sends its public key in the same unprotected response. To qualify a protected issuer requires independently provisioned signing-key custody, signed issuer identity, host permission/ACL negative tests, key rotation/revocation, a trusted monotonic clock or freshness authority, a durable rollback-resistant store or external anchor, and strict integration tests. None is installed or inferred here.

All tests run with disposable synthetic Ed25519 keys and isolated temporary SQLite files, including two simultaneous independent Python processes racing the same challenge (one accepted, one rejected), restart/reinstantiation replay refusal, a forged-signature denial before writing state, corrupted-ledger fail-closed, and explicit rollback-bypass falsification. No repository-scoped or shared database is created by tests; the test directories are temporary.

No private memory access, unapproved host commands, model weight change, shared Ollama process, protected merge or deployed host signing service is part of this candidate.
